### B. Adding a genuinely new feature (post-launch)

- Reuse the established patterns rather than inventing new ones: a
  `{from,to}` transition map for any new stateful resource (seven already
  exist — see `docs/ARCHITECTURE.md`), the idempotent
  "check-key-then-act-then-catch-23000-and-refetch" shape for anything
  triggered by a retryable client request, `AuditService::record()` for
  anything mutating, `WebhookDispatchService::dispatch()` (after commit)
  and `NotificationPreferenceService::filterChannels()` (inside `via()`)
  for anything that should notify externally.
- Before writing a policy's `view()`/`create()` on any tenant-scoped
  model, check whether a customer-portal login (`User::customerProfile()`)
  could reach it — Phase 10's one critical bug was exactly this shape
  (`branch_id === null` used as a staff-bypass that also silently matched
  every portal login) and it is easy to reintroduce in a new policy by
  copying an old one that predates the fix.
- Run the full exit-command suite (`composer validate --strict`,
  `vendor/bin/pint --test`, `php artisan migrate:fresh --seed`,
  `php artisan test`, `npm run typecheck`, `npm run build`) before calling
  any change done, the same discipline every phase in this project used.

## Guardrails

- Never trust ownership, status, totals, or tenant IDs from a client payload.
- Never query a tenant model in a job before restoring tenant context.
- Never use `withoutGlobalScopes()` without a reviewed reason and targeted company predicate.
- Never expose internal notes, costs, hidden events, document keys, or private customer data publicly.
- Never send broadcasts, notifications, or webhooks before transaction commit.
- Never modify shipment, delivery, or customs state directly from a controller.
- Preserve existing user changes and document assumptions.
